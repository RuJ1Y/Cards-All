# Supabase 学习路线

本文档用于约束“服务端 / Supabase 成员”的教学方式。当前项目后端主线只使用 Supabase，目标不是让 AI 代写一个看不懂的后端，而是让用户在做项目的过程中逐步理解后端开发。

## 1. 学习目标

短期目标：

- 会用 Supabase Auth 做登录和用户身份。
- 会设计论坛和游戏社区需要的数据表。
- 理解 PostgreSQL 表、字段、主键、外键、索引、约束。
- 理解 RLS 为什么重要，以及如何写基本权限策略。
- 会用 Storage 存头像、帖子图片、游戏资源相关文件。
- 会用 Realtime 做简单通知、评论刷新或状态同步。
- 知道 Edge Functions 适合放哪些逻辑。
- 会验证一次后端改动是否真的安全、可用、可维护。

长期目标：

- 通过 Supabase 理解传统后端里的数据库、鉴权、权限、接口、部署、日志和安全。
- 后续如果学习 Spring Boot、Ktor、NestJS 等自建后端，能知道它们分别在解决 Supabase 背后的哪些问题。

## 3. 学习顺序

### 第 1 阶段：Supabase 基础

要理解：

- Project、API URL、anon key、service role key 的区别。
- Auth 用户和业务用户资料表的区别。
- PostgreSQL 表、字段类型、主键、外键。
- SQL Editor 和 Table Editor 的区别。

项目任务：

- 建立用户资料表 `profiles`。
- 登录后能读取自己的资料。
- 普通用户不能读取不该看的隐私字段。

### 第 2 阶段：论坛数据模型

要理解：

- 帖子、评论、点赞、收藏之间的关系。
- 一对多、多对多如何建模。
- 什么时候需要唯一约束和索引。

项目任务：

- `posts`
- `comments`
- `post_likes`
- `post_favorites`
- 基础查询和分页。

### 第 3 阶段：RLS 权限

要理解：

- RLS 是数据库层权限，不是前端按钮隐藏。
- `auth.uid()` 代表当前登录用户。
- select、insert、update、delete 可以分别有策略。
- 管理员权限需要单独设计。

项目任务：

- 未登录用户可看公开帖子。
- 登录用户可发帖和评论。
- 用户只能编辑/删除自己的帖子。
- 管理员可以审核和隐藏帖子。

### 第 4 阶段：Storage 文件

要理解：

- Bucket、Object path、public/private bucket。
- 文件路径如何和数据库记录关联。
- 上传权限和读取权限要分别控制。

项目任务：

- 用户头像上传。
- 帖子图片上传。
- 图片和帖子记录绑定。

### 第 5 阶段：Realtime 与通知

要理解：

- Realtime 适合“数据变化后通知客户端刷新”。
- Realtime 不是万能 IM 后端。
- 通知表比纯前端事件更可靠。

项目任务：

- 评论后帖子作者收到通知。
- 点赞或收藏可以生成简单通知。
- 客户端能订阅自己的通知变化。

### 第 6 阶段：Edge Functions

要理解：

- Edge Function 适合放不该暴露在客户端的逻辑。
- 它不是必须品，普通 CRUD 不要硬塞进去。
- Function 要考虑鉴权、输入校验、错误响应和日志。

项目任务：

- 内容审核辅助逻辑。
- 管理员批量操作。
- 复杂通知聚合。
- 后期可能的排行榜刷新。

## 4. 不做自建后端的原因

当前用户后端基础较弱，暑假目标是做出完整项目并通过项目理解后端。自建后端会引入大量额外负担：

- 鉴权。
- 数据库连接。
- 权限系统。
- 文件上传。
- 部署。
- 日志。
- 安全。
- 接口文档。
- 运维。

这些能力以后都可以学，但当前阶段先通过 Supabase 把对应概念学明白。Supabase 不是逃避后端，而是把后端学习压缩到一个能交付项目的路径里。

## 5. 何时重新评估自建后端

只有满足以下条件，才重新讨论自建后端：

- Supabase 主线已经稳定。
- 论坛、游戏、管理后台已经有可演示版本。
- 用户已经理解基本数据库和权限设计。
- 有明确业务场景 Supabase 不适合解决。
- 用户主动要求把某个模块作为后端学习专项。

在此之前，不把自建后端作为当前计划。
