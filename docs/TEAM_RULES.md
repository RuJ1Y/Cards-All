# 团队协作规则

本文档约束所有 Codex 专精对话和人工协作。目标是让多个独立上下文像一个小团队一样工作，而不是各自凭记忆乱改。

## 1. 基本原则

- 每个成员只负责自己明确领取的范围。
- 开始前先阅读 `docs/PROJECT_CENTER.md`、本文档、当前任务相关文档和相关代码。
- 不允许凭空假设项目状态；能查代码就查代码，能跑验证就跑验证。
- 不允许为了省事绕开核心问题。
- 不允许为了快速交差牺牲长期架构。
- 不允许无记录地更换技术方案。
- 不允许同时让多个成员修改同一块代码，除非总控明确安排。

## 2. 标准工作流程

每个成员处理任务时，应按以下流程执行：

1. 读上下文：项目中枢、团队规则、相关文档、相关代码。
2. 明确任务边界：本次做什么，不做什么，影响哪些模块。
3. 制定小计划：复杂任务要拆成可验证步骤。
4. 实现：遵守现有架构和代码风格。
5. 自查：检查编译、测试、页面、接口、权限、错误处理。
6. 更新文档：同步接口、数据库、产品、架构或 ADR。
7. 管理 Git：查看变更，确认没有误改，按任务提交或给出提交建议。
8. 输出交接：说明完成内容、改动文件、验证结果、遗留问题、下一步。

## 3. 交接模板

每次成员完成任务，必须输出以下内容：

```text
本次角色：
本次目标：

已完成：
- 

改动文件：
- 

重要决策：
- 

验证结果：
- 

未完成/遗留问题：
- 

需要同步给其他成员：
- 

下一步建议：
- 
```

如果没有代码改动，也要说明“无代码改动”以及产出的文档、方案或决策。

## 4. Git 规则

所有成员必须保护已有工作。

- Godot 游戏端和 Android 论坛端优先各自独立 Git 仓库，不共用一个仓库。
- `D:\Cards-All` 根目录可以作为本地总工作区和文档中枢，不强制作为统一仓库。
- GitHub 展示时，每个核心端使用独立仓库和中英双语描述。
- 开始前检查当前目录是否是 Git 仓库。
- 如果是 Git 仓库，先查看 `git status --short`。
- 不回滚自己没有创建的改动。
- 不使用 `git reset --hard`、强制删除、强推等危险操作，除非用户明确要求。
- 不把无关格式化、无关重构和当前任务混在一起。
- 一个提交只表达一个主要意图。
- 提交信息要说明业务目的，不只写 `fix`、`update`。
- 如果根目录不是 Git 仓库，要检查具体子项目，例如 `godot/`。
- 跨子项目改动必须在交接中分别说明。

优先仓库规划：

```text
godot/ -> cards-godot-game
app/   -> cards-android-forum 或后续独立 Android 论坛项目仓库
```

GitHub 描述示例：

```text
Cards Godot game client / Cards 项目 Godot 游戏客户端
Android forum client for the Cards community / Cards 社区 Android 论坛客户端
```

建议提交格式：

```text
feat(forum): add post detail comments
fix(auth): handle expired session
docs(project): add team workflow rules
refactor(android): isolate Supabase repository
```

## 5. 文档规则

代码和文档必须一起演进。

- 数据库表、字段、RLS、Storage、Realtime 变化，要更新 `docs/DATABASE.md`。
- Ktor 后端学习路线、概念解释和阶段总结，要更新 `docs/KTOR_BACKEND_LEARNING.md`。
- Supabase 相关学习资料暂作为备用，要更新 `docs/SUPABASE_LEARNING.md`。
- API、RPC、Edge Function、请求/响应变化，要更新 `docs/API.md`。
- 页面流程、用户故事、验收标准变化，要更新 `docs/PRODUCT.md`。
- 模块边界、依赖方向、技术方案变化，要更新 `docs/ARCHITECTURE.md`。
- 重要技术取舍，要写入 `docs/adr/`。
- 临时交接总结，写入或汇总到 `docs/handoff/`。
- 总方向变化，必须更新 `docs/PROJECT_CENTER.md`。

不需要每次都写长文档，但必须让下一位成员能接上。

## 6. 技术取舍规则

本项目追求行业主流、稳定、可维护的实现。

默认要求：

- Android 使用现代 Kotlin 和 Jetpack 生态。
- Godot 使用 Godot 4.x 的稳定能力。
- 后端学习主线使用 Kotlin + Ktor；当前先做本地知识积累，不急着接入 Cards 项目主线。
- Web 管理后台优先 TypeScript、成熟前端框架和组件库。
- 数据结构优先使用数据库约束、索引、权限策略保证正确性。
- 接口契约优先清晰、可验证、可文档化。

遇到困难时必须按顺序处理：

1. 复现问题。
2. 定位原因。
3. 查官方文档或项目现有实现。
4. 做最小修复。
5. 验证修复。
6. 记录原因和方案。

禁止行为：

- 因为某个库一时报错，就换成手写低质量方案。
- 因为数据库、路由、序列化或 Gradle 报错，就绕开 Ktor 正规学习路径。
- 因为权限、鉴权、数据库连接复杂，就让客户端直接连接数据库。
- 因为状态管理麻烦，就把所有逻辑塞进 UI。
- 因为接口对接麻烦，就复制粘贴多个不一致的数据模型。
- 因为时间紧，就留下无法解释的硬编码。

允许降级的条件：

- 主流方案确实不适合当前项目阶段。
- 已尝试定位和解决，仍然成本过高。
- 降级不破坏长期架构。
- 已在交接或 ADR 中记录原因、影响和后续补救计划。
- 总控或用户接受该取舍。

## 7. 各成员职责规则

### 团队大脑 / 总控

- 维护项目目标、路线图、优先级。
- 拆分任务并控制范围。
- 审核成员交接。
- 发现冲突时更新中心文档。
- 决定是否进入下一阶段。

### 产品设计成员

- 产出用户故事和验收标准。
- 控制 MVP 范围。
- 避免需求无限扩张。
- 为毕设和求职准备项目叙事。

### 架构成员

- 先设计边界，再建议改代码。
- 输出数据流、模块图、接口契约。
- 对跨端共用概念统一命名。
- 对重大取舍写 ADR。

### 服务端 / Ktor 学习成员

- 当前职责是教学和知识积累，不以 Cards 项目功能交付为第一目标。
- 使用 Kotlin + Ktor 讲解后端开发，Ktor 是框架，Kotlin 是语言。
- 每次任务先解释要学的概念，再写代码或给操作步骤。
- 每次输出要包含本次涉及的概念，例如 HTTP、Route、Request、Response、JSON、DTO、Service、Repository、PostgreSQL、Connection、Migration、LAN。
- 不能只给代码；必须说明为什么这么设计、如何在本地运行、如何用浏览器/Apifox/PowerShell 验证。
- 本地数据库可以使用 PostgreSQL；客户端不得直接连接数据库，必须通过 Ktor API。
- 暂时不要求接入 Android、Godot 或 Web 管理后台；需要接入时由团队大脑重新安排。
- 如果用户明显不理解某个后端概念，要先用本项目里的例子解释，再继续推进实现。

### Android 前端成员

- UI 不直接承载复杂业务逻辑。
- 网络和 Supabase 调用应封装在 Repository 或数据层。
- 页面状态要覆盖加载、空状态、错误、成功。
- 关键用户路径要能自测。

### Godot 前端成员

- 游戏表现、游戏状态、网络通信要分离。
- 不把长期业务数据硬编码在场景脚本里。
- 资源命名和场景结构要可维护。
- 与后端同步的数据结构必须文档化。

### Web 管理后台成员

- 管理权限必须严格区分。
- 所有危险操作要有确认、反馈和错误提示。
- 列表、筛选、审核、封禁等操作要考虑真实运营场景。
- 不做只有静态页面没有管理能力的假后台。

### iOS 论坛成员

- 只有在主线稳定后再启动。
- 优先复用已有产品流程和接口契约。
- 不因 iOS 扩展影响暑假 MVP。

### 指导老师 / 毕设顾问成员

- 把工程内容整理成毕设语言。
- 检查题目工作量、创新点、系统设计完整性。
- 维护论文结构和答辩材料。

## 8. 自查清单

每次交付前至少检查：

- 是否符合本次任务范围。
- 是否误改无关文件。
- 是否有明显重复代码。
- 是否有临时硬编码、调试输出、无意义注释。
- 是否有错误处理。
- 是否有空状态或异常状态。
- 是否更新相关文档。
- 是否说明验证方式。
- 是否给下一位成员留下明确交接。

代码任务还应尽量检查：

- 编译是否通过。
- 单元测试或关键手动流程是否通过。
- 数据库迁移或权限策略是否可执行。
- 页面在常见尺寸下是否可用。
- 接口失败时是否有合理反馈。

## 9. 冲突处理

如果成员之间出现冲突，按以下优先级判断：

1. 用户最新明确指令。
2. `docs/PROJECT_CENTER.md`。
3. 已记录 ADR。
4. `docs/TEAM_RULES.md`。
5. 相关模块现有代码风格。
6. 成员自己的判断。

如果冲突无法判断，停止扩大改动，交给团队大脑或用户拍板。

## 10. 本项目的红线

以下行为视为不合格交付：

- 功能看似完成，但无法运行或无法验证。
- 为了方便绕过权限、安全、数据一致性。
- 用临时代码替代架构设计，且没有记录。
- 不读现有代码就重写一套。
- 修改大量无关文件。
- 不写交接，让下一个成员无法继续。
- 遇到困难直接换方向，却不解释为什么。
- 使用过时或小众技术，只因为当前更省事。

遇到困难时，要把困难暴露出来、定位出来、解决掉；如果真的解决不了，也要留下清楚的原因、尝试记录和下一步方案。
