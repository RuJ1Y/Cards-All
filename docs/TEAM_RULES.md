# 团队规则

所有成员必须遵守本文件。目标：少废话、可交接、不乱改、不偷懒。

## 1. 开工规则

开工前必须：

1. 读 `docs/PROJECT_CENTER.md`。
2. 读本文件。
3. 读自己角色相关文档。
4. 查当前 Git 分支和状态。
5. 明确本次只改什么，不改什么。

不能凭记忆工作。能查代码就查代码，能验证就验证。

## 2. 分支与提交

硬规则：

- 每位成员必须在自己的分支写代码或文档。
- 禁止直接在 `master` / `main` 上写代码、提交、合并、推送。
- 如果发现当前在 `master` / `main`，先创建个人任务分支。
- 分支名用短横线，不用 `/`，例如 `android-forum-post-list`、`ktor-learning-ping`。
- 开始前运行 `git status --short`，确认没有误碰他人改动。
- 不回滚、不覆盖、不格式化无关文件。
- 默认不提交、不合并、不推送。
- 完成后先交接：改了什么、怎么验证、还有什么风险。
- 只有用户确认后，才允许 commit、merge 到 `master` / `main` 或 push。
- 提交信息主要用中文；可保留少量英文 scope，例如 `docs(项目): 精简团队协作规则`。
- 如果用户要求由用户自己合并/提交，成员只保留工作区改动和交接说明。

如果无法创建分支或 Git 状态不清楚，停止扩大改动，先汇报。

## 3. 标准流程

1. 读上下文。
2. 建/切自己的分支。
3. 做小计划。
4. 实现。
5. 自查。
6. 更新必要文档。
7. 输出交接。
8. 等用户确认后再提交/合并。

## 4. 交接模板

每次结束必须输出：

```text
本次角色：
本次目标：
所在分支：

已完成：
- 

改动文件：
- 

验证结果：
- 

遗留问题：
- 

需要同步给其他成员：
- 

建议下一步：
- 
```

## 5. 文档规则

- 文档要短，优先写结论、规则、路径。
- 不写长篇解释，细节放角色文档或交接。
- 新规则只写一个地方，其他文件引用它。
- 数据库/API/架构变化必须更新对应文档。
- 历史交接可能过期，必须对照 `PROJECT_CENTER.md`。

## 6. 技术规则

- 用行业常用、稳定、现代的技术。
- 遇到困难先解决，不为了方便换低质量方案。
- 不把业务逻辑塞进 UI。
- 不让客户端直连数据库。
- 不绕过权限、安全、错误处理。
- 不留下无法解释的硬编码。
- 换方案必须说明原因、影响和补救计划，并等用户确认。

诊断顺序：

1. 复现问题。
2. 定位原因。
3. 查官方文档或现有代码。
4. 最小修复。
5. 验证。
6. 记录。

## 7. 角色规则

- 总控：维护目标、任务、优先级、验收和同步。
- 产品：控制 MVP 范围，输出用户流程和验收标准。
- 架构：维护模块边界、数据流、接口契约和 ADR。
- Ktor 后端学习：教学优先，讲清 HTTP、Route、JSON、PostgreSQL、分层、局域网访问。
- Android：UI -> 状态/ViewModel -> Repository/API，不让后端细节散落 Activity。
- Godot：表现、状态、网络分离，不把长期数据硬编码在场景脚本。
- Web 后台：权限、审核、用户、公告、统计要像真实后台。
- iOS：主线稳定后再启动。
- 毕设顾问：把工程成果整理成论文和答辩表达。

## 8. 红线

以下行为不合格：

- 未读文档就改。
- 在 `master` / `main` 直接改、提交、合并或推送。
- 未经用户确认就 commit / merge / push。
- 遇到困难直接换路子但不说明。
- 修改大量无关文件。
- 功能无法运行或无法验证。
- 不交接。

冲突优先级：用户最新指令 > `PROJECT_CENTER.md` > ADR > 本文件 > 现有代码风格。
