# 项目中枢文档

本文档是 Cards-All 项目的最高层事实来源。所有专精对话在开始工作前，都应先阅读本文档和 `docs/TEAM_RULES.md`，再结合自己负责的代码目录开展工作。

## 1. 项目定位

Cards-All 不是单一小游戏，也不是单纯论坛项目，而是一个围绕原创卡牌/策略游戏展开的多端社区产品。

核心形态：

- Godot 游戏客户端：承载主要游戏体验。
- 论坛前端：承载玩家交流、攻略、反馈、内容沉淀。
- 后端学习支线：当前使用 Kotlin + Ktor 学习后端基础，先在本地和局域网跑通数据库、HTTP API、JSON、鉴权和基本部署概念；暂不急着接入项目主线。
- Web 管理后台：承担用户管理、内容审核、公告、配置、数据查看。
- iOS 论坛端：作为可能扩展方向，优先级低于 Android/Godot/Web 管理后台。

项目要同时服务三个目标：

- 暑假和一个学期内做出可演示、可答辩、可长期维护的完整版本。
- 一年后作为下一份实习申请的核心项目。
- 为毕业设计提供足够完整的需求、设计、实现、测试和部署材料。

## 2. 阶段目标

### 暑假 MVP

时间范围：暑假剩余一个多月。

目标：完成一个能完整演示的最小可用版本；后端部分允许先作为学习支线，不强行承担项目交付。

必须完成：

- 用户登录/注册。
- 论坛帖子列表、详情、发布、评论。
- Godot 游戏基础可玩流程或可交互原型。
- 后端学习支线跑通 Ktor `/ping`、本地 PostgreSQL 连接和最小 CRUD 示例。
- Web 管理后台最小版本：帖子审核、用户查看、公告管理至少完成其中一到两个。
- 项目 README、演示截图、基础部署说明。

暂缓完成：

- 完整 IM 系统。
- 复杂联机对战。
- 复杂推荐算法。
- 大而全的运营后台。
- iOS 端完整实现。

### 学期完善版

时间范围：暑假后一个学期。

目标：把 MVP 打磨成毕设和实习简历都能讲清楚的完整项目。

重点方向：

- 完善游戏玩法、状态保存、战斗记录或排行榜。
- 完善论坛社区能力：点赞、收藏、关注、通知、搜索、举报。
- 完善管理后台：审核、封禁、公告、配置、基础数据统计。
- 完善架构文档、接口文档、数据库文档、测试文档。
- 形成可展示部署环境和录屏材料。

### 一年后求职版

目标：项目不仅能跑，还能体现工程能力。

应具备：

- 清晰模块边界。
- 可复用组件和服务层。
- 数据权限和安全设计。
- 关键业务有测试或可重复验证方案。
- 有线上部署或本地一键启动方案。
- 有完整项目介绍、技术难点、架构图、简历表述。

## 3. 团队成员与分工

这里的“成员”指不同 Codex 对话或不同工作线程。每个成员上下文独立，不自动同步，必须通过文档和 Git 状态交接。

### 团队大脑 / 总控

职责：

- 维护本文档、路线图、任务拆解和优先级。
- 决定阶段范围，控制需求膨胀。
- 协调 Android、Godot、服务端、Web 管理后台之间的接口契约。
- 汇总各成员交接，更新项目事实。
- 在技术分歧时做最终取舍。

### 产品设计成员

职责：

- 定义目标用户、核心场景、页面流程。
- 把需求拆成可实现的用户故事。
- 控制功能优先级，区分必须做、应该做、以后做。
- 输出页面流程、验收标准、毕设叙事角度。

### 架构成员

职责：

- 设计模块边界、目录结构、数据流和依赖方向。
- 设计未来项目后端的模块边界、数据库关系、接口契约和客户端调用方式。
- 当前先帮助后端学习支线建立正确概念，不急着把 Ktor 接入 Godot、Android 或管理后台。
- 审核技术方案是否能长期维护。
- 对关键决策写 ADR。

### 服务端 / Ktor 学习成员

职责：

- 使用 Kotlin + Ktor 带用户学习后端开发。
- 先做知识积累和本地实验，不急着服务 Cards 项目主线。
- 讲清楚 HTTP、路由、请求/响应、JSON 序列化、数据库连接、Repository/Service 分层、错误处理、日志和局域网访问。
- 本地数据库优先 PostgreSQL，可用 Docker 或本机安装；客户端不直接连接数据库，只通过 Ktor API 访问。
- 每次后端任务都要输出“这次你应该理解什么”，帮助用户逐步建立后端能力。
- 后续是否把 Ktor 后端接入项目，由团队大脑在学习到一定阶段后重新评估。

### Android 前端成员

职责：

- 负责 Android 论坛端或综合 App。
- 维护 UI、ViewModel、Repository、状态管理、错误处理。
- 与后端 API 契约对接；在后端学习阶段可以先使用 mock 数据或本地 Ktor 示例接口。
- 保持 UI 层不直接散落后端细节。
- 输出页面状态、接口依赖和自测结果。

### Godot 前端成员

职责：

- 负责 Godot 游戏客户端。
- 实现游戏场景、交互、资源加载、基础玩法。
- 与后端同步用户、战斗记录、排行榜或配置数据。
- 保持游戏逻辑、表现层、网络层清晰分离。

### Web 管理后台成员

职责：

- 负责后台管理系统。
- 实现内容审核、用户管理、公告、配置、统计等功能。
- 使用主流 Web 技术栈，优先 TypeScript 和成熟组件生态。
- 严格区分管理员权限和普通用户权限。

### iOS 论坛成员

职责：

- 作为低优先级扩展成员。
- 在核心项目稳定后，再评估是否用 SwiftUI 实现论坛浏览、发帖、评论等功能。
- 不应抢占暑假 MVP 的主线资源。

### 指导老师 / 毕设顾问成员

职责：

- 从毕设角度审查题目、范围、创新点和工作量。
- 帮助沉淀开题报告、论文目录、系统设计、测试和答辩材料。
- 把工程成果翻译成学校能理解的论文表达。

## 4. 技术路线

当前主路线：

- 游戏客户端：Godot 4.x。
- Android 客户端：Kotlin，优先使用现代 Android 架构和 Jetpack 生态。
- 后端学习：Kotlin + Ktor，PostgreSQL，kotlinx.serialization，Gradle，必要时使用 Exposed 或 JDBC 理解数据库访问。
- 后端策略：当前后端先不承担项目主线交付，优先做知识积累；等用户理解基础后，再决定使用 Supabase、Ktor，或二者如何分工。
- Web 管理后台：TypeScript，现代前端框架和成熟 UI 组件库。
- 可能的 iOS 客户端：SwiftUI。
- 版本管理：Godot 游戏端和 Android 论坛端优先使用各自独立 Git 仓库，不共用一个仓库；提交粒度要能表达一次完整意图。

## 5. GitHub 展示策略

短期不使用一个大而全的 monorepo。`D:\Cards-All` 作为本地总工作区和文档中枢，各核心端先独立管理 Git 历史，方便单独展示、单独迭代、单独写简历描述。

优先仓库：

- Godot 游戏端仓库：对应 `godot/`，用于展示游戏客户端、玩法、资源、场景和与后端交互能力。
- Android 论坛端仓库：对应 `app/` 或后续新建的 Android 论坛项目目录，用于展示 Android 客户端、论坛流程、状态管理和 Supabase 对接能力。

暂缓仓库：

- Web 管理后台：等最小后台成型后再决定是否单独建仓库。
- Ktor 后端学习仓库：先作为本地学习实验，等形成稳定小项目后再决定是否单独建仓库。
- iOS 论坛端：低优先级扩展，启动后再单独建仓库。

GitHub 仓库命名建议：

```text
cards-godot-game
cards-android-forum
```

GitHub 仓库描述必须中英双语，便于国内老师、同学和未来面试官同时理解。

示例：

```text
Cards Godot game client / Cards 项目 Godot 游戏客户端
Android forum client for the Cards community / Cards 社区 Android 论坛客户端
```

技术选择原则：

- 优先使用行业最新、常用、稳定的技术。
- 不为了省事选择明显落后、不可维护、难扩展的方案。
- 遇到困难时，先定位原因并尝试解决。
- 只有当主流方案确实不适合当前阶段，才允许降级或替换，并必须记录原因。
- 新技术必须服务项目目标，不能为了炫技牺牲进度和稳定性。

## 6. 代码质量要求

所有成员必须遵守：

- 架构清晰：UI、状态、业务逻辑、数据访问、外部服务边界清楚。
- 可复用：重复出现的逻辑要沉淀为组件、函数、服务或模块。
- 可维护：命名清楚，文件职责单一，避免随手堆代码。
- 可测试：关键业务逻辑应能通过单元测试、集成测试或明确手动流程验证。
- 可运营：数据库权限、内容审核、错误处理、日志、配置和部署要考虑长期使用。
- 可交接：每次任务结束必须说明改了什么、为什么改、怎么验证、遗留问题。

## 7. 当前最高优先级

暑假阶段优先级如下：

1. 后端学习支线先跑通 Ktor 基础：`/ping`、路由、JSON、配置和本地启动。
2. 本地部署 PostgreSQL，理解数据库、表、主键、外键、索引和连接方式。
3. 用 Ktor 写最小 CRUD 示例，理解 API 如何包住数据库。
4. 暂时不强行把后端接入 Cards 项目，避免学习和产品交付互相拖累。
5. Godot、Android 论坛和 Web 管理后台继续按产品节奏推进时，可先使用 mock 数据或临时接口。
6. 沉淀文档、截图、演示和毕设材料。
7. 等后端基础稳定后，再评估 Supabase、Ktor 或混合架构。
